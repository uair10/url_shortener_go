# ТЗ: сервис коротких ссылок `shortener`

HTTP-сервис коротких ссылок (как bit.ly).
Документ описывает продукт как набор тикетов: эпики → задачи → бизнес-правила и критерии приёмки.

---

## 1. Процесс разработки

1. **Один тикет - одна ветка:** `git switch -c SHR-7-create-link`. В конце merge в `main`.
2. **Сначала тест, потом код** - как минимум для бизнес-правил.
3. **Definition of Done** (общий для всех тикетов):
   - `make` проходит полностью (tidy, fmt, lint, test -race, vuln);
   - каждое бизнес-правило (`BR-x.y`) покрыто хотя бы одним тестом, имя теста или комментарий ссылаются на номер правила;
   - OpenAPI-спецификация обновлена (с SHR-5 и дальше);
   - у экспортируемых имён есть doc-комментарии;
   - нет `//nolint` без объяснения причины.
4. **Зависимости.** В продакшен-коде до SHR-19 только стандартная библиотека. Исключения:
   - `github.com/caarlos0/env/v11` - чтение конфига из переменных окружения (SHR-2);
   - `github.com/oapi-codegen/oapi-codegen/v2` - как tool для генерации кода (SHR-5);
   - `github.com/getkin/kin-openapi` - только в тестах, для контрактных проверок (SHR-5);
   - `golang.org/x/sync` - после собственной реализации параллельной обработки (SHR-15).

## 2. Глоссарий

| Термин | Значение |
|---|---|
| Ссылка | Пара «короткий код → исходный URL» плюс метаданные |
| Код | Короткий идентификатор в пути: `https://sho.rt/aB3xK9q` |
| Alias | Код, выбранный пользователем, а не сгенерированный |
| Владелец | Пользователь, создавший ссылку |
| Переход | Запрос `GET /{code}`, завершившийся редиректом |
| Активная ссылка | Не удалена, не деактивирована, срок жизни не истёк |
| Квота | Лимит на **количество** активных ссылок у пользователя |
| Лимит частоты | Лимит на **число запросов** за интервал времени |

## 3. Роли

| Роль | Как определяется | Что может |
|---|---|---|
| Аноним | Без заголовка `X-API-Key` | Переходить по ссылкам, регистрироваться |
| Пользователь | Валидный `X-API-Key` | Управлять **своими** ссылками |
| Администратор | Заголовок `X-Admin-Token` совпадает с конфигом | Модерация (SHR-23) |

## 4. Нефункциональные требования (для всех эндпоинтов)

- **NFR-1.** Тела запросов и ответов в JSON. Запрос с телом, у которого `Content-Type` не `application/json`, → 415.
- **NFR-2.** Максимальный размер тела 1 MiB, больше → 413.
- **NFR-3.** Время - в UTC, формат RFC 3339 (`2026-10-09T12:00:00Z`).
- **NFR-4.** Все ошибки в едином формате (см. SHR-3).
- **NFR-5.** Каждый ответ содержит заголовок `X-Request-ID` (см. SHR-4).
- **NFR-6.** API-ключи, токены и тела запросов **никогда** не попадают в логи.
- **NFR-7.** Внутренние детали ошибок (текст ошибки БД, стектрейс) никогда не отдаются клиенту.
- **NFR-8.** Сервис корректно завершается по SIGTERM, не теряя запросы, которые уже обрабатываются (см. SHR-2).
- **NFR-9.** Все списки отдаются с пагинацией.

## 6. Справочник ошибок

Формат: RFC 9457 Problem Details, `Content-Type: application/problem+json`.

```json
{
  "type": "https://sho.rt/errors/quota-exceeded",
  "title": "Quota exceeded",
  "status": 403,
  "detail": "Active links limit reached: 100",
  "code": "quota_exceeded",
  "request_id": "01J9..."
}
```

| `code` | HTTP | Когда |
|---|---|---|
| `malformed_json` | 400 | Тело не парсится, лишние поля, неверный тип поля |
| `invalid_query` | 400 | Неверные query-параметры |
| `validation_failed` | 422 | Данные синтаксически верны, но нарушают правила. Есть поле `errors: [{"field", "reason"}]` |
| `unauthorized` | 401 | Нет ключа или ключ неверный |
| `forbidden` | 403 | Нет прав (например, неверный admin-токен) |
| `quota_exceeded` | 403 | Превышена квота активных ссылок |
| `not_found` | 404 | Ресурса нет **или он чужой** |
| `method_not_allowed` | 405 | Неверный метод |
| `alias_taken` | 409 | Код/alias занят |
| `email_taken` | 409 | Email уже зарегистрирован |
| `link_gone` | 410 | Ссылка удалена, деактивирована, истекла или заблокирована |
| `payload_too_large` | 413 | Тело больше лимита |
| `unsupported_media_type` | 415 | Не JSON |
| `rate_limited` | 429 | Лимит частоты. Обязателен заголовок `Retry-After` (секунды) |
| `internal` | 500 | Всё неожиданное. Детали только в лог |

Почему такие коды:
- **400 и 422.** 400 означает «не смог прочитать запрос», 422 - «прочитал, но данные нарушают правила».
- **429, а не 409, для лимита частоты.** 409 означает конфликт состояния ресурса. Для «слишком часто» есть специальный 429, и клиенты, прокси и SDK умеют его обрабатывать (ретраи по `Retry-After`).
- **403, а не 400, для квоты.** Запрос корректен, но пользователю сейчас запрещено это действие. Повторять бессмысленно, пока не освободится квота.
- **404, а не 403, для чужой ссылки.** Чтобы не раскрывать, что такой код существует.

## 7. Архитектурные решения

### ADR-001. Внедрение зависимостей без DI-контейнера

**Контекст.** Во многих экосистемах (Java/Spring, Python/dishka) зависимости собирает DI-контейнер: провайдеры, скоупы, автоматическое разрешение графа. Нужно решить, нужен ли он здесь.

**Решение.** Контейнер не используем. Зависимости собираются вручную в одной функции - **composition root** (`run()` в `cmd/shortener` или `internal/app`). Каждый компонент получает зависимости через конструктор `NewXxx(deps...)`.

**Почему так принято в Go**
- Компилятор сам проверяет граф: не передал зависимость - код не собирается. Валидация графа происходит на этапе компиляции и ничего не стоит.
- Нет рефлексии и магии: по коду `run()` видно, что от чего зависит, а «Go to definition» в IDE ведёт в нужное место.
- Ошибка сборки графа - это обычная ошибка из конструктора, а не исключение из глубин библиотеки.

**Запрещено**
- глобальные переменные с зависимостями;
- инициализация зависимостей в `init()`;
- service locator (передача «контейнера» внутрь компонентов);
- зависимости в `context.WithValue`.

**Когда composition root разрастётся**, вынеси сборку в пакет `internal/app` с функцией `New(cfg) (*App, error)` и разбей на функции по фичам. Это всё ещё ручная сборка.

### ADR-002. Слои

```
cmd/shortener/                    composition root: конфиг, сборка зависимостей, запуск
internal/<фича>/                  доменные типы, бизнес-правила, интерфейсы хранилищ (users, links, ...)
internal/httpapi/                 HTTP: роутинг, JSON, ошибки, middleware
internal/infrastructure/          технический слой; сам каталог кода НЕ содержит
    config/                       package config: загрузка и валидация конфига из env
    logging/                      package logging: сборка *slog.Logger
    storage/{memory,postgres}/    реализации хранилищ
    ratelimit/, clients/<api>/    прочие технические компоненты, внешние API
```

**`infrastructure` - каталог, а не пакет.** Каждый подкаталог - отдельный пакет с именем по тому, что он даёт (`config.Load`, `postgres.NewRepo`), а не по слою. Причины:
- имя пакета видно в каждом вызове: `infrastructure.NewXxx` ничего не говорит о том, что делает функция;
- циклический импорт в Go - ошибка компиляции; общий пакет тянет в каждого импортёра все зависимости (драйвер БД, клиенты) и создаёт риск цикла;
- неэкспортированные имена видны всему пакету, поэтому в общем пакете между компонентами нет границ.

**Запрещено:** файлы `.go` прямо в `internal/infrastructure/`, пакеты `utils`, `common`, `helpers`.

Правило зависимостей: `httpapi` → домен ← `infrastructure/storage`. Домен не импортирует ни `net/http`, ни драйвер БД, ни `infrastructure`.
Интерфейс хранилища объявляется **в домене** («accept interfaces, return structs»).

### ADR-003. Ограничение in-memory состояния

Лимиты частоты и (до SHR-19) данные хранятся в памяти процесса. При нескольких репликах лимиты считаются отдельно в каждой реплике. Для учебного проекта это допустимо. В реальности понадобился бы Redis.

## SHR-2. Каркас сервиса: конфиг, логи, graceful shutdown

**Тип:** Story

> **Как** инженер эксплуатации, **я хочу**, чтобы сервис настраивался через переменные окружения и корректно останавливался, **чтобы** его можно было запускать в Docker/Kubernetes без потери запросов.

**Бизнес-правила**
- **BR-2.1.** Конфиг читается из переменных окружения (раздел 5). Отсутствующая необязательная переменная → значение по умолчанию.
- **BR-2.2.** Ошибки конфига выводятся **все сразу**, а не только первая, и процесс завершается с кодом 1 до запуска сервера.
- **BR-2.3.** Логи в JSON (`log/slog`), уровень из `LOG_LEVEL`.
- **BR-2.4.** По SIGINT/SIGTERM сервер перестаёт принимать новые соединения, дожидается текущих запросов не дольше `SERVER_SHUTDOWN_TIMEOUT` и завершается с кодом 0.
- **BR-2.5.** Порт занят → в лог, код выхода 1.
- **BR-2.6.** `GET /healthz` → 200 с телом `{"status":"ok"}` без авторизации.
- **BR-2.7.** У HTTP-сервера выставлены таймауты чтения заголовков, чтения, записи и простоя.
- **BR-2.8.** Все зависимости собираются в одной функции (ADR-001).

**Критерии приёмки**
- [ ] Table-driven тест загрузки конфига: значения по умолчанию, переопределение, несколько ошибок одновременно.
- [ ] Вручную: долгий запрос (временный `time.Sleep`) + Ctrl+C → запрос завершается, затем процесс выходит.
- [ ] Вручную: два экземпляра на одном порту → второй выходит с кодом 1.

## SHR-3. Единый формат ошибок

**Тип:** Technical story

> **Как** разработчик клиента API, **я хочу** получать ошибки в одном предсказуемом формате с машиночитаемым кодом, **чтобы** обрабатывать их без парсинга текста.

**Бизнес-правила**
- **BR-3.1.** Любая ошибка - в формате из раздела 6, `Content-Type: application/problem+json`.
- **BR-3.2.** Поле `code` - из справочника, стабильно и не меняется между версиями.
- **BR-3.3.** Ошибки валидации (422) содержат **все** нарушенные поля сразу:
  `"errors": [{"field": "url", "reason": "scheme must be http or https"}]`.
- **BR-3.4.** Неизвестная ошибка → 500 `internal`, текст ошибки только в лог (NFR-7).
- **BR-3.5.** 404 на несуществующий путь и 405 на неверный метод тоже отдаются в этом формате.
- **BR-3.6.** Слишком большое тело → 413, не-JSON → 415, битый JSON или неизвестные поля → 400.

**Критерии приёмки**
- [ ] Table-driven тест: каждый `code` из справочника, который можно получить на этом этапе, → правильный HTTP-статус и формат.
- [ ] Тест: 500 не содержит в ответе текст исходной ошибки.

## SHR-4. Middleware: request ID, access log, recovery

**Тип:** Technical story

**Бизнес-правила**
- **BR-4.1.** Входящий `X-Request-ID` (до 64 символов `[A-Za-z0-9-]`) используется как есть, иначе генерируется новый.
- **BR-4.2.** `X-Request-ID` возвращается в каждом ответе и есть в каждой строке лога, относящейся к запросу, и в теле ошибок (`request_id`).
- **BR-4.3.** Access log: метод, путь (**без query-строки**), статус, длительность, размер ответа, request ID.
- **BR-4.4.** Паника в обработчике → 500 `internal`, стек в лог, сервер продолжает работать.
- **BR-4.5.** `GET /healthz` не пишется в access log (шум от проб Kubernetes).

**Критерии приёмки**
- [ ] Тест: паникующий обработчик → 500, следующий запрос к тому же серверу успешен.
- [ ] Тест: переданный ID возвращается, невалидный заменяется новым, без ID генерируется.

## SHR-5. Документация API

**Тип:** Story

> **Как** разработчик клиента, **я хочу** открыть интерактивную документацию API в браузере, **чтобы** понять контракт без чтения кода.

**Бизнес-правила**
- **BR-5.1.** Спецификация OpenAPI 3.1 лежит в репозитории (`api/openapi.yaml`) и является источником истины о контракте.
- **BR-5.2.** Описаны все эндпоинты, схемы запросов и ответов, **все возможные ошибки** каждого эндпоинта, примеры, схема авторизации `X-API-Key`.
- **BR-5.3.** `GET /openapi.yaml` отдаёт спецификацию, `GET /docs` - интерактивную документацию (Swagger UI, Redoc или Scalar).
- **BR-5.4.** Спецификация встроена в бинарник, внешних файлов при запуске не нужно.
- **BR-5.5.** Спецификация проходит линтер в pre-commit.
- **BR-5.6.** Расхождение кода и спецификации ловится автоматически (тестом или генерацией).

**Критерии приёмки**
- [ ] `/docs` открывается в браузере, из него можно отправить запрос к `/healthz`.
- [ ] Линтер спецификации в pre-commit.
- [ ] Сломай контракт намеренно (переименуй поле в ответе): проверка падает.

# Эпик B. Пользователи

## SHR-6. Регистрация и API-ключи

**Тип:** Story

> **Как** новый пользователь, **я хочу** зарегистрироваться по email и получить API-ключ, **чтобы** управлять своими ссылками.

**API**

`POST /users` - без авторизации
```json
// запрос
{"email": "dev@example.com"}
// ответ 201
{"id": "u_01J9...", "email": "dev@example.com", "api_key": "shr_k7Hq...", "created_at": "2026-10-09T12:00:00Z"}
```

`GET /users/me` - с `X-API-Key` → 200 (без `api_key`).

**Бизнес-правила**
- **BR-6.1.** Email обязателен, валиден, не длиннее 254 символов, хранится в нижнем регистре.
- **BR-6.2.** Email уникален без учёта регистра. Повтор → 409 `email_taken`.
- **BR-6.3.** Ключ имеет формат `shr_` + 32 случайных символа и показывается **только один раз** в ответе на регистрацию.
- **BR-6.4.** Ключ хранится **только в виде хэша**. Утечка хранилища не раскрывает ключи.
- **BR-6.5.** Эндпоинты, требующие авторизации: нет заголовка или ключ неверный → 401 `unauthorized`. Ответ одинаковый в обоих случаях.
- **BR-6.6.** Ключ не попадает в логи (NFR-6).
- **BR-6.7.** Регистрация ограничена: 5 запросов в час с одного IP → 429.

**Критерии приёмки**
- [ ] Тесты на каждое BR.
- [ ] Тест: в хранилище нет исходного ключа.
- [ ] Тест: `GET /users/me` без ключа, с неверным и с верным ключом.

# Эпик C. Ссылки

## SHR-7. Создание короткой ссылки

**Тип:** Story · **Размер:** крупный, разбит на подзадачи

> **Как** пользователь, **я хочу** отправить длинный URL и получить короткий, **чтобы** делиться им.

**API**

`POST /links` - `X-API-Key` обязателен
```json
// запрос
{"url": "https://go.dev/doc/effective_go"}
// ответ 201
{
  "code": "aB3xK9q",
  "short_url": "http://localhost:8080/aB3xK9q",
  "url": "https://go.dev/doc/effective_go",
  "status": "active",
  "created_at": "2026-10-09T12:00:00Z",
  "expires_at": null,
  "visits": 0
}
```

**Бизнес-правила: URL**
- **BR-7.1.** Схема только `http` или `https`.
- **BR-7.2.** Хост обязателен и является доменным именем. IP-адреса (v4/v6) и `localhost` запрещены (защита от SSRF, см. SHR-17).
- **BR-7.3.** Длина URL не больше `MAX_URL_LENGTH`.
- **BR-7.4.** Нельзя сокращать ссылки на сам сервис (хост из `BASE_URL`), иначе получится цикл редиректов.
- **BR-7.5.** Домены из `BLOCKED_DOMAINS` запрещены **вместе с поддоменами**: блок `evil.com` запрещает `a.evil.com`, но не `notevil.com`.
- **BR-7.6.** Нарушения BR-7.1–7.5 → 422 `validation_failed` с перечислением всех причин.

**Бизнес-правила: код**
- **BR-7.7.** Код - `CODE_LENGTH` символов из алфавита `[A-Za-z0-9]`, криптографически случайный. При коллизии генерируется новый, не больше 3 попыток, затем 500.

**Бизнес-правила: лимиты**
- **BR-7.8.** Не больше `CREATE_RATE_LIMIT` (10) запросов на создание за **скользящие** 60 секунд на пользователя. Превышение → 429 `rate_limited`, заголовок `Retry-After` = число секунд (с округлением вверх), через которое освободится место в окне.
- **BR-7.9.** Не больше `MAX_ACTIVE_LINKS` (100) активных ссылок у пользователя. Превышение → 403 `quota_exceeded`. Удалённые, деактивированные и истёкшие не считаются.
- **BR-7.10.** Порядок проверок: авторизация → лимит частоты → формат запроса → валидация → квота. Запрос, отклонённый по лимиту частоты, **тоже** расходует лимит.

**Бизнес-правила: идемпотентность**
- **BR-7.11.** Если у пользователя уже есть **активная** ссылка на тот же URL, созданная без alias и TTL, и новый запрос тоже без них, возвращается существующая ссылка с кодом **200** (а не 201). Квота не расходуется.
- **BR-7.12.** URL сравниваются после нормализации: схема и хост в нижнем регистре, порт по умолчанию (`:80`/`:443`) убирается. Путь, query и fragment сравниваются как есть.

**Подзадачи**
- [ ] SHR-7.a. Доменный тип ссылки, валидация URL, доменные ошибки.
- [ ] SHR-7.b. Интерфейс хранилища ссылок + in-memory реализация.
- [ ] SHR-7.c. Rate limiter со скользящим окном.
- [ ] SHR-7.d. Сервис: генерация кода, квоты, идемпотентность.
- [ ] SHR-7.e. HTTP-обработчик + OpenAPI.

**Критерии приёмки**
- [ ] Table-driven тест валидации: минимум 12 случаев (по одному на каждое правило плюс граничные: ровно `MAX_URL_LENGTH`, `MAX_URL_LENGTH+1`, `EVIL.com`, `notevil.com`, `[::1]`, `127.0.0.1`).
- [ ] Тест BR-7.8: 10 запросов проходят, 11-й → 429 с корректным `Retry-After`; после сдвига часов на 60 секунд снова можно.
- [ ] Тест BR-7.9: 100-я ссылка создаётся, 101-я → 403; после удаления одной снова можно (вернёшься к нему после SHR-11).
- [ ] Тест BR-7.11 и BR-7.12: `HTTPS://GO.DEV:443/x` и `https://go.dev/x` - одна ссылка.
- [ ] Тест коллизии: генератор кода подменён и возвращает занятый код 2 раза → успех, 3 раза → 500.
- [ ] Тест хранилища на конкурентность с `-race`.

## SHR-8. Переход по короткой ссылке

**Тип:** Story

> **Как** любой посетитель, **я хочу** открыть короткую ссылку и попасть на исходный URL.

**API:** `GET /{code}` и `HEAD /{code}`, без авторизации.

**Бизнес-правила**
- **BR-8.1.** Активная ссылка → **302 Found**, заголовок `Location`. Не 301: браузер закэширует 301 навсегда, и переходы перестанут считаться и управляться.
- **BR-8.2.** Заголовок `Cache-Control: private, max-age=0`.
- **BR-8.3.** Каждый `GET`-переход увеличивает счётчик ссылки на 1 и обновляет `last_visit_at`. `HEAD` редиректит, но **не** считается.
- **BR-8.4.** Нет такого кода → 404 `not_found`.
- **BR-8.5.** Удалена, деактивирована, истекла или заблокирована → 410 `link_gone`. Счётчик не меняется.
- **BR-8.6.** Не больше `REDIRECT_RATE_LIMIT` (120) переходов за скользящую минуту с одного IP → 429 с `Retry-After`.
- **BR-8.7.** Счётчик не теряет переходы при параллельных запросах.
- **BR-8.8.** Сравнение кода чувствительно к регистру: `aB3` ≠ `ab3`.

**Критерии приёмки**
- [ ] Тест: 100 параллельных переходов → счётчик ровно 100 (с `-race`).
- [ ] Тесты на все BR.
- [ ] HTTP-клиент в тестах не следует редиректу.

## SHR-9. Просмотр ссылки

**Тип:** Story

**API:** `GET /links/{code}` - `X-API-Key`.

**Бизнес-правила**
- **BR-9.1.** Владелец видит ссылку в любом статусе, включая истёкшие и деактивированные. Удалённые не видит (404).
- **BR-9.2.** Чужая или несуществующая ссылка → 404 `not_found`. Ответы неотличимы.
- **BR-9.3.** Ответ: поля из SHR-7 плюс `last_visit_at` (или `null`).
- **BR-9.4.** Поле `status` вычисляется на момент запроса: ссылка, у которой истёк срок, показывается как `expired`, даже если фоновая очистка ещё не сработала.

**Критерии приёмки**
- [ ] Тест BR-9.2: сравнение тел ответов для «чужой» и «несуществующей» ссылки (кроме `request_id`).
- [ ] Тест BR-9.4 с подменёнными часами.

## SHR-10. Список своих ссылок

**Тип:** Story

**API:** `GET /links?status=active&limit=20&offset=0` - `X-API-Key`.

```json
{"items": [ ... ], "total": 57, "limit": 20, "offset": 0}
```

**Бизнес-правила**
- **BR-10.1.** Только ссылки текущего пользователя, удалённые не показываются.
- **BR-10.2.** Сортировка: сначала новые (`created_at` по убыванию). При равенстве - по коду (стабильный порядок).
- **BR-10.3.** `limit`: по умолчанию 20, от 1 до 100. `offset`: по умолчанию 0, не меньше 0. Нарушение → 400 `invalid_query`.
- **BR-10.4.** Фильтр `status`: `active`, `disabled`, `expired`. Без фильтра - все, кроме удалённых. Неизвестное значение → 400.
- **BR-10.5.** `total` - общее число ссылок с учётом фильтра, а не размер страницы.
- **BR-10.6.** `offset` больше `total` → 200 с пустым `items` (не `null`!).

**Критерии приёмки**
- [ ] Table-driven тест параметров (граничные значения 0, 1, 100, 101, -1, `abc`).
- [ ] Тест BR-10.6: в JSON `"items": []`, а не `"items": null`.

## SHR-11. Удаление ссылки

**Тип:** Story

**API:** `DELETE /links/{code}` - `X-API-Key`. Ответ 204 без тела.

**Бизнес-правила**
- **BR-11.1.** Удалять может только владелец. Чужая или несуществующая → 404.
- **BR-11.2.** Удаление мягкое (soft delete): ссылка помечается удалённой, статистика сохраняется в хранилище.
- **BR-11.3.** Повторное удаление → 404 (уже не видна владельцу, BR-9.1).
- **BR-11.4.** Удалённая ссылка перестаёт учитываться в квоте (BR-7.9) сразу.
- **BR-11.5.** Код удалённой ссылки **нельзя** использовать как alias в течение `CODE_REUSE_COOLDOWN` (30 дней). Иначе злоумышленник займёт код популярной ссылки и перехватит переходы. Попытка → 409 `alias_taken`.

**Критерии приёмки**
- [ ] Тест BR-11.4: при квоте 100 → удаление → создание успешно.
- [ ] Тест BR-11.5 с подменёнными часами: день 29 → 409, день 31 → 201.

## SHR-12. Пользовательский alias

**Тип:** Story

**API:** в `POST /links` новое необязательное поле `"alias": "go-docs"`.

**Бизнес-правила**
- **BR-12.1.** От 3 до 32 символов: латиница, цифры, `-`, `_`. Начинается с буквы или цифры.
- **BR-12.2.** Alias хранится и сравнивается **в нижнем регистре**: `Go-Docs` и `go-docs` - один alias. При этом сгенерированные коды остаются чувствительными к регистру (BR-8.8).
- **BR-12.3.** Зарезервированные слова запрещены: `links`, `users`, `docs`, `openapi.yaml`, `healthz`, `readyz`, `admin`, `api`, `metrics`, `static` → 422.
- **BR-12.4.** Занят (активной, неактивной или недавно удалённой ссылкой, BR-11.5) → 409 `alias_taken`.
- **BR-12.5.** Alias не может совпадать ни с одним существующим сгенерированным кодом и наоборот: генератор при коллизии с alias делает повторную попытку.
- **BR-12.6.** Запрос с alias не подпадает под идемпотентность BR-7.11.

## SHR-13. Срок жизни ссылки (TTL)

**Тип:** Story

**API:** в `POST /links` новые необязательные поля, взаимоисключающие:
`"expires_in": "24h"` **или** `"expires_at": "2026-12-31T23:59:59Z"`.

**Бизнес-правила**
- **BR-13.1.** Указаны оба поля → 422.
- **BR-13.2.** `expires_in`: формат длительности Go (`30m`, `24h`), от 1 минуты до `MAX_TTL`.
- **BR-13.3.** `expires_at`: в будущем, минимум через 1 минуту, не дальше `MAX_TTL` от текущего момента.
- **BR-13.4.** Без полей - бессрочная ссылка, `expires_at: null`.
- **BR-13.5.** После наступления `expires_at` переход → 410, ссылка не учитывается в квоте, но видна владельцу со статусом `expired`.
- **BR-13.6.** Ссылки с TTL не подпадают под идемпотентность BR-7.11.

## SHR-14. Деактивация и активация

**Тип:** Story

**API:** `PATCH /links/{code}` с телом `{"active": false}` → 200 и обновлённая ссылка.

**Бизнес-правила**
- **BR-14.1.** Только владелец (иначе 404).
- **BR-14.2.** Деактивированная ссылка: переход → 410, в квоте **не** учитывается.
- **BR-14.3.** Повторная активация проверяет квоту (BR-7.9) → 403 при превышении.
- **BR-14.4.** Нельзя активировать истёкшую или заблокированную администратором ссылку → 422.
- **BR-14.5.** **Изменить исходный URL нельзя.** Попытка передать `url` → 400 (неизвестное поле). Причина: ссылки уже распространены, подмена цели - вектор атаки.
- **BR-14.6.** Запрос без изменений (активировать активную) → 200, ничего не меняется (идемпотентность).

## SHR-15. Пакетное создание

**Тип:** Story

**API:** `POST /links/batch` - `X-API-Key`.
```json
// запрос
{"items": [{"url": "https://go.dev"}, {"url": "https://pkg.go.dev", "alias": "pkg"}]}
// ответ 201
{"items": [ {...}, {...} ]}
```

**Бизнес-правила**
- **BR-15.1.** От 1 до `BATCH_MAX_SIZE` (50) элементов, иначе 422.
- **BR-15.2.** «Всё или ничего»: если хотя бы один элемент невалиден, не создаётся ни одна ссылка → 422, в `errors` поле указывается как `items[3].url`.
- **BR-15.3.** Дубликаты alias внутри пакета → 422.
- **BR-15.4.** Пакет из N элементов расходует N единиц лимита частоты (BR-7.8) и требует N свободных мест в квоте (BR-7.9). Не хватает → 429/403 до начала создания.
- **BR-15.5.** Порядок ответа совпадает с порядком запроса.
- **BR-15.6.** Обработка параллельная, не больше `BATCH_WORKERS` одновременно. Отмена запроса клиентом останавливает обработку.

**Критерии приёмки**
- [ ] Тест порядка.
- [ ] Тест BR-15.2: после ошибки в хранилище нет ни одной ссылки из пакета.
- [ ] Тест BR-15.6: после отмены контекста новые задачи не запускаются (счётчик вызовов через `sync/atomic`).

# Эпик D. Аналитика

## SHR-16. Статистика переходов по дням

**Тип:** Story

**API:** `GET /links/{code}/stats?days=7` - `X-API-Key`, только владелец.
```json
{"code": "aB3xK9q", "total": 42, "daily": [{"date": "2026-10-03", "visits": 0}, ... {"date": "2026-10-09", "visits": 12}]}
```

**Бизнес-правила**
- **BR-16.1.** `days` от 1 до 90, по умолчанию 7.
- **BR-16.2.** Дни считаются по UTC, последний день - сегодня (неполный).
- **BR-16.3.** В ответе **все** дни периода, включая дни без переходов (`visits: 0`), по возрастанию даты.
- **BR-16.4.** Сумма `daily` может быть меньше `total` (переходы до начала периода).

## SHR-17. Проверка доступности ссылок

**Тип:** Story

**API**
- `POST /links/{code}/check` → `{"alive": true, "status": 200, "checked_at": "...", "latency_ms": 123}`
- `POST /links/check` - проверить все активные ссылки пользователя.

**Бизнес-правила**
- **BR-17.1.** Проверка - `HEAD`-запрос на исходный URL. Ответ 405 на `HEAD` → повтор через `GET` (тело не читается).
- **BR-17.2.** Таймаут `CHECK_TIMEOUT` (3 секунды) на каждую ссылку. Таймаут, ошибка DNS или соединения → `alive: false`, `status: null`, поле `error` с кратким описанием.
- **BR-17.3.** `alive: true` для статусов 2xx и 3xx. Редиректы не выполняются.
- **BR-17.4.** Массовая проверка: не больше 10 одновременно, общий таймаут 30 секунд, результаты в порядке `created_at`.
- **BR-17.5.** **SSRF-защита:** запрос не выполняется, если хост резолвится в приватный, loopback или link-local адрес → `alive: false, error: "forbidden address"`.
- **BR-17.6.** Не чаще 1 раза в минуту на ссылку, повторный запрос → 429.

# Эпик E. Фоновые процессы

## SHR-18. Фоновая очистка

**Тип:** Technical story

**Бизнес-правила**
- **BR-18.1.** Каждые `CLEANUP_INTERVAL` удаляются **окончательно** ссылки, у которых истёк срок или которые мягко удалены больше `CODE_REUSE_COOLDOWN` назад.
- **BR-18.2.** Из лимитеров частоты удаляются ключи без запросов за последнее окно (иначе память растёт бесконечно).
- **BR-18.3.** Каждый запуск пишет в лог: сколько удалено, сколько заняло.
- **BR-18.4.** Ошибка очистки логируется, но не останавливает ни воркер, ни сервис.
- **BR-18.5.** При shutdown воркер завершается, сервис дожидается его завершения.

- **BR-19.4.** Отмена HTTP-запроса отменяет SQL-запрос.
- **BR-19.5.** `GET /readyz` → 200, если БД доступна, иначе 503.

**Критерии приёмки**

## SHR-20. Кэш редиректов

**Тип:** Story

- **BR-20.1.** Горячие ссылки отдаются из кэша в памяти (LRU, `CACHE_SIZE` = 10 000 записей).
- **BR-20.2.** Деактивация, удаление и блокировка инвалидируют кэш **сразу**. Устаревший редирект недопустим.
- **BR-20.3.** Счётчик переходов считается и при попадании в кэш.

# Эпик G. Эксплуатация

## SHR-21. Docker и CI

- **BR-21.1.** `Dockerfile`: multi-stage, итоговый образ `gcr.io/distroless/static` (или `scratch`), запуск не от root.
- **BR-21.2.** Версия, коммит и дата сборки вшиты в бинарник и отдаются в `GET /version`.
- **BR-21.3.** CI на каждый PR: lint, test -race, govulncheck, сборка образа. PR нельзя смержить с красным CI.

## SHR-22. Метрики и профилирование

- **BR-22.1.** `GET /metrics` в формате Prometheus на **отдельном** порту (`METRICS_PORT`): число запросов и гистограмма длительности по маршруту и статусу, число переходов, число активных ссылок.
- **BR-22.2.** Метка маршрута - **шаблон** (`/links/{code}`), а не реальный путь. Почему? (Кардинальность.)
- **BR-22.3.** `pprof` доступен только на внутреннем порту.

## SHR-23. Модерация (опционально)

- **BR-23.1.** `POST /admin/links/{code}/block` с `{"reason": "phishing"}` - заголовок `X-Admin-Token`. Неверный токен → 403.
- **BR-23.2.** Заблокированная ссылка: переход → 410, владелец видит статус `blocked` и причину, активировать не может (BR-14.4).
- **BR-23.3.** Сравнение токена - за постоянное время.
- **BR-23.4.** Действие пишется в лог аудита: кто (IP), что, когда, причина.
